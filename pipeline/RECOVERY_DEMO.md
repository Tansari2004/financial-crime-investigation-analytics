# Replay, correction, and publication recovery

This walkthrough uses the real ingestion, promotion, correction, and publication
functions with a tiny fabricated fixture. It does not rerun the 5.08-million-row
IBM dataset, refresh Power BI, or establish production banking performance.

## Run one command

Prerequisites: Python 3.10+, installed project dependencies
(`python -m pip install -e .`), and PostgreSQL 16 with a local role allowed to
create databases. From the repository root:

```sh
python scripts/demo_banking_recovery.py
```

The default admin connection is `postgresql:///postgres`. For another local
instance, set `BANKING_DEMO_ADMIN_DSN` or pass `--admin-dsn`. The connection is
used only to create and drop a fresh `banking_demo_<random UUID>` database. The
script has no option to reuse an existing database. Only the new database gets
schemas, test data, and the deliberate fault; it is removed on success or failure.

Outputs go to `data/processed/recovery-demo/` (ignored by Git). Choose another
directory with `--output-dir`. A successful run writes `report.json`,
`transcript.txt`, three input CSVs under `inputs/`, and the complete before/after
publication snapshots. A nonzero exit status means a required check failed.

## Recorded run

The [saved report](evidence/recovery_demo/report.json) and
[terminal transcript](evidence/recovery_demo/transcript.txt) were generated by
the script against an isolated local PostgreSQL 16 instance. The command used
`--admin-dsn postgresql://127.0.0.1:55439/postgres`; this port is specific to that
verification environment, not a requirement. The report records the UTC run time.

| Step | Actual observation | Published rows | Published USD total | Publication |
| --- | --- | ---: | ---: | ---: |
| Initial load | Four source rows: three accepted, one duplicate candidate retained in raw/quarantine | 3 | 60.00 | 1 |
| Replay same bytes | File and publication both skipped; counts and all published rows unchanged | 3 | 60.00 | 1 |
| Explicit correction | Original 10.00 preserved; correction 15.00 recorded and made current | 3 | 65.00 | 2 |
| Quality failure | New 40.00 payment deliberately transformed to 999.00; amount reconciliation blocked publication | 3 | 65.00 | 2 |
| Repair and publish | Restore the new payment's staged 40.00 amount; zero currency imbalances | 4 | 105.00 | 3 |

### What the failure proves

The script first ingests and promotes a valid additional payment, then directly
alters its core paid amount **inside the disposable database only**. This
simulates a faulty transformation; it is not a recommended production edit.
Publication raises `amount reconciliation failed` and records one analytics
failure. The script compares every row of `publication_state`, `publication_run`,
`fact_daily_transaction`, `fact_risk_signal`, `file_row_reconciliation`, and
`file_amount_reconciliation` with the preceding publication. All six snapshots
remain identical; the upstream core state and operational failure log are
deliberately outside that published snapshot.

Compare the saved [before](evidence/recovery_demo/before_failed_publication.json)
and [after](evidence/recovery_demo/after_failed_publication.json) snapshots. The
repair restores the staged amount, then reruns publication. The rejection limit
remains 5%; no quality threshold is relaxed. Publication IDs and timestamps are
run-specific. The script does not expect gapless database sequences after a
rollback.

### Why the duplicate is only a candidate

The fixture deliberately repeats one exact payment. The first valid payload is
accepted; the repeated payload is kept in raw storage and quarantine but does
not enter the published fact. This prevents double counting for this example.
The same rule could exclude a legitimate repeated payment in a real source with
no durable identifier. An upstream transaction/event ID plus explicit version
semantics would provide stronger evidence; a matching hash alone does not.

## Continuous verification

The banking CI workflow runs the same command against its PostgreSQL service,
then uploads the generated evidence. This complements the existing database
tests; it does not replace malformed-input, late-arrival, concurrency, or scale
testing. No external data download or model/provider call is needed.
